# Electron 壳子评估报告（师座桌面版可行性）

> 日期：2026-08-08 · 状态：评估稿，未执行
> 目的：评估把师座 Web 版包成 Electron 桌面应用的形态、成本与收益

---

## 1. 结论先行

**可以做，且是解决「文件浏览器打开」需求的正确路径，但建议推迟**——先用 Web 版（海外部署）验证场景价值，确认老师真的需要桌面版再套壳。原因：Electron 壳子本身不改变产品价值，只改变分发/体验；而它带来 4 类成本（体积、安全、签名、更新）。

---

## 2. Electron 壳子是什么样

```
┌─────────────────────────────────────────────┐
│ Electron 主进程 (Node.js)                    │
│   - 启动本地静态服务 (Express 托管 Next 产物)  │
│   - 或直接加载 build 后的 Next 静态文件        │
│   - 系统集成：打开文件管理器、托盘、自动更新    │
└──────────────┬──────────────────────────────┘
               │
┌──────────────▼──────────────────────────────┐
│ Electron 渲染进程 (Chromium)                 │
│   - 师座前端 (Next.js 构建产物, 不变)         │
│   - 原生能力：对话框、文件系统、拖拽           │
└──────────────┬──────────────────────────────┘
               │ HTTP /api/llm (本地或远程)
┌──────────────▼──────────────────────────────┐
│ 后端 (pi SDK + 中转站)                       │
│   方案A：打包进 Electron (主进程跑 Node 后端)  │
│   方案B：独立 Node 服务 (更简单，先这样)       │
└─────────────────────────────────────────────┘
```

### 2.1 两种打包方式

| 方式 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A. 本地全包** | Next build 产物 + pi SDK 后端全打进 exe，`npm run dev` 逻辑内置 | 离线可用、数据全本地 | 体积大、后端代码要适配 Electron 主进程 |
| **B. 壳 + 远程后端** | Electron 只装前端壳，后端仍在服务器 | 壳轻（~100MB）、后端不用改 | 需联网、依赖服务器 |

**推荐 B**：师座后端（pi SDK + 中转站调用）逻辑复杂，硬塞进 Electron 主进程风险大；壳 + 远程后端改动最小，且中转站在线才能用，离线价值不大。

### 2.2 Electron 壳能解锁的能力（相对 Web）

| 能力 | Web 版 | Electron 版 |
|------|--------|-------------|
| 打开本地文件浏览器（右键→在文件夹中显示） | ❌ | ✅ `shell.showItemInFolder(path)` |
| 直接读写本地目录（成果存到老师指定文件夹） | ❌（仅下载） | ✅ 对话框选目录 + fs 写入 |
| 文件拖拽 | ⚠️ 图片可 | ✅ 任意文件 |
| 系统托盘 / 全局快捷键 | ❌ | ✅ |
| 自动更新 | ❌ | ✅ electron-updater |
| 双击即用（老师不用记网址） | ❌ | ✅ |
| 离线缓存 | ❌ | ✅（可选） |

## 3. 成本评估

### 3.1 工作量

| 项 | 估算 |
|----|------|
| Electron 主进程 + 窗口 + 本地静态服务 | 0.5-1 天 |
| 打包配置（electron-builder，Windows exe / macOS dmg） | 0.5-1 天 |
| 「打开所在文件夹」+ 成果目录选择（解锁的核心需求） | 0.5 天 |
| 自动更新（可选） | 0.5-1 天 |
| 测试（Windows 为主 + 必要 macOS） | 0.5 天 |
| **合计（MVP 壳）** | **约 2-3 天** |

> 前置依赖：需安装 Node 20+（已有）、npm 包 `electron` / `electron-builder`（约 100-200MB 下载）。macOS 打包需 Mac 机器（或 CI）。

### 3.2 成本清单（不可忽略）

| 成本 | 说明 |
|------|------|
| **体积** | 每个安装包约 **80-120MB**（Electron 内嵌 Chromium + Node） |
| **签名** | Windows 无签名 → SmartScreen 警告「未知发布者」；签名证书约 **¥1000+/年**（OV 证书） |
| **更新维护** | 老师机器上装了旧版 → 需自动更新机制 + 服务端托管更新包 |
| **安全面** | Electron 主进程有 Node 权限，代码要严格隔离（`contextIsolation: true`） |
| **平台碎片** | Windows 10/11 + 可能的 macOS，都要测 |

### 3.3 收益评估

| 收益 | 强度 | 说明 |
|------|------|------|
| 打开文件浏览器（老师刚需 #4） | 高 | 但 Web 版「保存到本机」已能凑合 |
| 双击即用、降低使用门槛 | 中 | 老师要自己下安装包，比点链接麻烦 |
| 离线下用 | 低 | 中转站在线才有效，离线意义不大 |
| 分发（官网下载 vs 浏览器直接开） | 中 | 需额外下载流程 + 更新管理 |

---

## 4. 关键决策点（如果要做）

1. **打包方式**：选 B（壳 + 远程后端）——后端不动，只包前端壳。
2. **成果落地**：Electron 版把「保存到本机」升级为「选择文件夹保存」+「在文件夹中显示」按钮（对应你的需求 #4）。
3. **签名**：MVP 阶段可先不出钱买证书（接受 SmartScreen 警告提示「仍要运行」）；正式分发再买。
4. **更新**：MVP 先不做自动更新，发布新版本让老师重新下载（或加 electron-updater）。

---

## 5. 建议路径（阶段化）

```
现在（Web MVP 验证）
  └─ 海外部署 → 老师浏览器打开链接 → 填 Key 用 → 验证场景价值
        │
        ▼ 老师反馈「需要桌面版 / 需要本地文件」时再启动
Electron 壳（约 2-3 天）
  ├─ 壳 + 远程后端
  ├─ 「在文件夹中显示」+ 选择保存目录
  └─ Windows 安装包分发（不签名，接受 SmartScreen 提示）
```

**为什么建议后置**：Electron 不改变「填 Key → 选场景 → 生成」的核心价值，只解决分发和文件操作；先确认老师真的愿意用（M2 试用反馈），再花 2-3 天做壳，避免过早投入。

---

## 6. 备选：Tauri（更轻的替代）

| 项 | Tauri | Electron |
|----|-------|----------|
| 安装包体积 | **3-10MB**（用系统 WebView） | 80-120MB |
| 内存占用 | 低 | 高 |
| 后端语言 | Rust（需装 Rust 工具链） | Node.js（现有栈直接复用） |
| 学习成本 | 中（Rust） | 低（纯 JS/Node） |
| 文件操作能力 | ✅ 同样支持 | ✅ 同样支持 |

> 若最终选择桌面化：技术栈偏 JS 团队用 Electron 最顺；追求极致体积/性能、且愿意学 Rust，用 Tauri。当前评估按 Electron 写，因为与现有 Next.js + Node 栈无缝衔接。

---

## 7. 结论

- **能做**：Electron 壳约 2-3 天，能真正解锁「右键在文件浏览器中打开」+ 本地成果目录。
- **建议**：现阶段不执行。先完成 Web 版海外部署 + M2 试用；收到老师「需要桌面版」的真实反馈后，用「壳 + 远程后端」方案落地，MVP 阶段不买签名证书。
- **决策门**：如果 M2 试用中「保存成果后找不到文件」成为高频反馈，提前启动 Electron 壳。
